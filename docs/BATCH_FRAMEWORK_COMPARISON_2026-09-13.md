# 批级 Harness 两份框架对照与并行交接建议

日期：2026-09-13
状态：Planner 复核与实现分工建议。比较现有规格，不改 Opus 原稿，不替代 AGENTS.md §5.9，不表示两条实验线已经收到任务或启动。

## 1. 结论

两份设计的批级材料与共享训练定义基本一致；实质分歧是 Fast 控制研究过程的范围。
Opus 版是“固定研究流程中的批级策略生成器”；Workflow 版是“可调用工具、组织比较并提交方案的批级研究执行者”。
两者适合成为同一系统中的两种控制器。建议共享材料、训练、权限、反馈与预算底座，在 Fast 控制层保留对照，不把整个项目复制成两套长期演化的协议。

Opus 版更易实现、调用较少、程序选择规则可复现；Workflow 版更贴近用户提出的完整观察—决策—执行研究对象，但调用成本和行为变异更高。
这些是结构与成本判断，尚无两方案的性能比较。自主程度更高不保证结果更好。

## 3. 方法差异

| 问题 | Opus 草案 | Workflow 规格 | 判断 |
|---|---|---|---|
| 决策与训练单位 | 一批 32 实体，一条策略展开为全批材料，共享训练 | 相同；区分 Research Workflow、Material Plan 和实际数组 | 基本一致，可共用 |
| 观察怎样产生 | 预设逐实体特征、批摘要，包含近邻等描述；部分材料描述按需算 | 全批概览后，Fast 主动调用数据/材料检查工具 | 观察内容丰富与是否能主动补查是不同能力 |
| Fast 输出什么 | 一次调用一个含 default/rules 的 JSON 策略 | 多次受限工具调用，产生候选材料、比较轨迹和 commit | 实质不同 |
| 实验如何安排 | 固定两轮，每轮提案、评价、按门更新 incumbent | Fast 在工具与预算内安排补查、候选、比较和停止 | 实质不同 |
| 谁提交最终方案 | 程序依据 C_A 的 candidate_improvement 决定是否替换 | Fast 依据合法 C_A 证据 commit；Runtime 检查资格，不重新排序 | 实质不同；两种选择器都有研究价值 |
| Slow 影响什么 | 一次改 Specific 或 General 正文；实际主要影响下一条策略 | 一次聚焦观察、构造、实验或决策指导之一 | 后者可编辑的行为位置更明确 |
| 局部损失诊断 | 存盘，但完全不供 Slow 使用 | 供贡献、集中度和风险诊断；禁止当作单条训练材料的因果标签 | 建议两线共同保留合法诊断 |
| 第一阶段 | M0 杠杆预检；M1 编译器；M2 Fast；M3 Slow | 首包贯通 Fast—整体反馈—commit—Slow—后续重执行 | 推进顺序不同 |
| 统计与规模 | K=4；三个形成作业；固定统计替换门 | 首包 K=3；两个作业；没有通用统计晋升门 | 原样运行不能作为公平控制器比较 |

Opus 的 default/rules 策略语言可直接作为 Workflow 的 build_material 输入。它是一个可复用组件，与工具循环并不互斥。

Opus 的明确 C_A 替换规则不是旧 C_B 隐藏覆盖的同一个实现问题：它可成为合法的固定选择器基线。
但它回答的是“Agent 能否提出更好的候选”，不能据此证明 Agent 学会了更好的交付决策。

Workflow 首版的“安排实验”仍受既定接口限制：可补查、选择下一候选、比较已完成结果或停止；不包含任意增加 seed、开放新标签块或更换 Consumer。
如果某条 Skill 建议的动作尚无工具或预算支持，必须标为未实现能力，不能只凭文字声称已接通。

## 5. 并行应怎样拆

### 公共底座：指定单一写入负责人

共同维护 Job/ConsumerSpec、T/C_A/C_B/E 权限、父对/scaler、Policy→Material 编译、共享训练、配对反馈、缓存及账本。
建议由 Opus 提取现有数值原语并落实 Policy 编译；另一线先针对接口做控制器开发，不同时修改同一数值模块。
保留历史 scratch 包只读。公共原语进入正常项目模块，避免另一个 scratch 的可变全局 config 串线。

公共底座必须做到：
- 一份完整 Policy 展开后真实共同训练；规则可条件化，不要求所有实体相同；
- 同 Job、参数、donor/增强流、材料和训练 seed 才能判定可复用，不能仅凭简化 assignment 文本认定跨作业模型别名；
- 反馈包含配对差、时间块与实体贡献；诊断不自动生成动作标签；
- 逻辑反馈机会与实际拟合/LLM成本分别计账；缓存不构成新证据；
- 两条线的 C_B 都在本批决定冻结后，E 都在规定输出冻结后开放。

### P 线：固定流程的 Policy 控制器（建议 Opus 主责）

保留“整批观察→一次策略→固定轮次评价→显式 C_A 替换规则”的方法核心。
实现范围聚焦 policy schema/compile/random_policy、固定两轮控制器、实际决策日志及边界 Slow。
记录每次保留 incumbent 的原因：主动策略保留、统计门未通过、或调用失败。这些情况不能合并成成功的 Agent 决策。
Slow 的 General/Specific 修改只能影响真实存在的行为入口；局部贡献诊断按共同底座开放。
这条线用于回答：固定实验流程下，批级策略生成和历史知识是否有价值。

### W 线：自主工具循环（主规格；建议另一独立实现线）

按现有首包任务书实现 overview/inspect_data/inspect_material/build_material/evaluate/compare/commit。
复用 P 线材料编译器，Fast 决定在预算内补查什么、比较哪些已完成候选、何时停止及提交什么。
接入四类指导，但一次自然 Slow 更新只改一个主要行为机制；KEEP 是允许出口。
这条线用于回答：允许 Agent 改善观察、构造、比较与决策过程，是否带来额外效用或成本优势。

两线可在独立控制器模块或独立工作树开发；合流的是公共接口与可比较工件。
若使用工作树，必须带入当前有效的未提交规格及必要源码；直接从旧 HEAD 新建空分支会丢失本次新设计。不得通过 stash/reset 清走他线工作，也不为此提交全部脏工作区。

## 6. 第一轮如何比较

先完成各自接线，不把 M0 新网格放回前置。运行前统一比较配置：
- 相同的已曝光 a55/a65、32 实体、Consumer、动作/参数范围、初始 H0 与固定增强基线；
- 相同训练 seed 列表、增强材料随机流和每次比较的重复数。当前 K=3/K=4 是待统一的实验配置，不保留为两线隐含差异；
- 相同新候选评价机会和最大物理训练预算；额外观察与 LLM 调用单列成本；
- 相同标签权限、全部分支提交后的 C_B、统一冻结后的 E；
- 随机搜索与固定增强基线保留，不能只比较两个 Agent；
- 第一张表先报告流程完成、实际材料/选择变化、效用与成本。一次开发运行不能证明 Source 积累。

不能把现有两个任务包的预算简单相加后自动启动。P/W 的新增比较应有独立、完整且有界的统一账本。
当前 Workflow 首包仍按原任务书处理；本文不扩大其 33 次拟合尝试上限。

首次 P/W 比较是两种完整控制方案的比较，同时改变了主动观察、调度和选择。若以后要归因“仅是哪一个环节带来提升”，再做单环节对照，不把初次差值直接归给某一个 hook。
