## 0. 直接说明与唯一主问题

每作业有四份未评分合法草案、两个新候选评估名额。先随机指定其中一份Q：

- 自主臂可忽略Q；
- 文字臂收到“先确保评估Q”的建议，可不采纳；
- 配额臂必须实际评估Q，才可正常提交；另一份候选仍可自选。

**主问题：同池、同训练预算上限下，将一项明确的随机探索建议变成可执行配额，能否改善实际交付或完整成本？** 同时用纯随机搜索和固定Menu检查收益是否需要Agent。

## 4. 草案与随机探索标记：两条独立冻结流

阶段2只开T，复用现役 `policy.random_policy` 分布和编译器：

```text
proposal_seed(j) = 2026091500 + 1000*job_index + j，j=0..63
按j升序生成并编译当前32实体assignment。
排除与None、Fixed或已有草案assignment相同者。
最先保留4份，标D1..D4；64次不足4份则该Job DRAFT_POOL_INCOMPLETE。
```

不按材料距离、复杂度、预测、代理分或人工合理性挑草案；不把a85旧D1或旧政策正文放入生成器。保持现役生成分布，不声称在全策略空间均匀。

在4份草案确定后，用另一条独立流随机排列草案ID：

```text
rng = numpy.random.RandomState(2026091600 + 1000*job_index)
pi = ['D1','D2','D3','D4'] 按 rng.permutation(4) 得到的顺序
Q = pi[0]；纯Random臂评估pi[0]和pi[1]
```

Q在任何拟合或C_A打开前确定，不随Agent第一选择变化，不重新抽签。它代表随机探索位置，不代表置信度、质量、最大距离或推荐的算子。两个Job的草案池、pi/Q均先冻结，再开始任何拟合。

三个Agent臂获得完全相同的4份草案、原overview及 `random_probe_id=Q`，说明它是随机标记、无效果证据。Q在开跑前即可见，允许Agent据此规划；不得声称它是第一项决策冻结后独立抽出的随机干预。自主臂也是“同池＋同随机标记”的新对照，不冒充旧G3的F_select原样重放。

只提供已有草案字段与T覆盖，不自动build全部材料，不附额外inspect_material诊断。所有Agent可自主用原build/inspect工具；这些工作照常记工具次数、墙钟与存储。

## 6. 硬配额的执行语义与最小实现

本节是唯一新增的流程约束，只作用于F_quota。

- build和inspect不占评估名额，可看任意池内草案。
- 第一次新评估可选Q或其他草案。
- Q尚未完整拟合且已有一份非Q新候选时，第二份新评估必须是Q；不能先消耗两份非Q名额后再要求第三份。
- Q尚未完整拟合时，任何commit（包括None/Fixed）均在写commit文件前被拒绝。
- Q三seed实际完整后解除提交前置要求；最终选择可以不用Q。
- 身份按编译后assignment比较，不能靠改名绕过；基线不满足Q配额。Q来自排除了基线的池。
- 拒绝使用既有ToolInputError和至多2次纠正预算，错误说明缺少Q及合法下一步；不执行同响应被拒绝动作后的后缀，不自动补训、替Agent提交或伪造评估事件。

建议在现役run_job新增默认关闭的薄执行检查入口，例如Adapter的 `check_evaluate` / `check_commit`，缺省不做事；具体命名由执行者决定。评估检查必须在新增候选计数/拟合预算预留之前，提交检查必须在绑定committed和落盘之前。校验不改材料、seed或评分，不把日志回调当成隐藏执行器。

所有动作照常经run_job真实调用build/evaluate/commit。Q的完整状态从当前已拟合候选及恢复后的真实记录推导，不新增hash链或另一套训练/恢复状态机。既有别名与候选预算语义保留；相同assignment可以满足Q身份，不能额外获得第三个评估名额。

若Agent连续不遵守合同导致纠正预算耗尽，按现役METHOD_INCOMPLETE收口，报告配额导致的失败率和已花成本；不能把这些臂删掉后宣称硬规则只有收益。传输、权限错误与非有限预测继续用原故障语义。a65上一包的绝对/相对索引问题本轮不顺手改成另一种权限规则。
