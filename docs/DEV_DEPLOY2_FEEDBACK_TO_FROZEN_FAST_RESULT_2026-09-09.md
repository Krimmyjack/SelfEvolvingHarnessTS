## 0. 执行中的事故与修复（先说清楚，避免读者带着错误假设看结果）

过程中发生一次账户余额耗尽事故，корр正过程本身也发现并修了几个真实代码
缺陷，如实记录：

1. **nowaterapi 账户余额耗尽**：初次发车覆盖120次决策时，账户在跑到
   g1/C/u13 中途（第4条）耗尽，后续6个批次（g2的C/R/F×u12/u13，共120条）
   连锁失败。
2. **故障分类器漏判**（真实代码缺陷，已修）：账户耗尽返回的
   `403 insufficient_user_quota`／中文"用户额度不足"没有被
   `dev_seq2_knowledge._fault_kind` 的关键词表覆盖，导致账户故障被当成
   普通单序列故障处理——脚本没有停线，反而把后续批次"正常跑完"，
   实际全是空数据。已在 `run_dev_deploy1._fault_kind` 加一层不影响原有
   分类的补充判断修复，并验证新老错误消息分类均正确。
3. **CLI 不按故障退出**（真实代码缺陷，已修）：批次内部提前中止时，
   `main()` 原来一律返回退出码0，外层脚本"非零退出就停"形同虚设。
   已改为批次提前中止时返回退出码2。
4. **分母/UNKNOWN 语义缺陷**（真实代码缺陷，已修）：批次没跑满时，均值
   原来是"能读几条就对几条求均值"，会用可读子集冒充整批均值。已改为
   population 不全就整体记 UNKNOWN，可读子集单列为诊断值——这正是本任务
   书第五节明确要求的语义。
5. **本地中转 HTTPS 校验冲突与更正**：用户提供的本地中转
   `http://127.0.0.1:8318/v1` 只支持明文 HTTP；最初尝试直接放宽
   `agent_backend.py::_validate_base_url` 的做法有严重副作用——该文件
   内容被 `methods/ttha/harness/compiler.py::_dependency_shas()`
   显式纳入每个 Harness 快照的身份哈希计算，编辑它会导致包括冻结 K0
   在内的所有快照身份漂移。已撤销该文件的源码改动（确认与 git 历史逐字节
   一致），改为运行时猴子补丁（`run_dev_deploy1.allow_loopback_http_relay`，
   `--allow-loopback-relay` 显式开关），只放行到
   `127.0.0.1`/`localhost`/`::1` 的 HTTP，不落盘、不影响身份哈希、
   不影响任何其他包的默认行为。
6. **模型身份对齐**：用户明确"以收据为准"——现有运行记录的模型是
   `gpt-5.6-sol`，不是 terra。补跑通过新中转请求别名 `cpa-gpt-5.6-sol`，
   核验返回身份精确为 `gpt-5.6-sol`（连续3次一致），与原120条决策使用
   的模型身份完全相同，两段决策未混用模型。

处理方式：136条故障记录先备份原始记录到
`_scratch/dev_deploy2/run1/_corrupted_2026-09-09_account_exhaustion/`
（含检查点与输出文件两份，一字不改），再从可续跑检查点中摘除故障行

## 1. 六次 Slow 修订：写了什么，选择了哪个面

| 组 | 臂 | 结果 | 目标面 | 暴露 |
|---|---|---|---|---|
| g1 | R | 编译成功 | `candidate_policy.selection_guidance`（PATCH） | 40/40 |
| g1 | C | 编译成功 | `candidate_policy.selection_guidance`（PATCH） | 40/40 |
| g1 | C-minus | **弃权（NO_UPDATE）** | — | — |
| g2 | C-minus | **弃权（NO_UPDATE）** | — | — |
| g2 | C | 编译成功 | 新增 `skill_library.entries/high_missingness_extreme_deviation_guard`（ADD） | **8/40** |
| g2 | R | 编译成功 | `candidate_policy.selection_guidance`（PATCH） | 40/40 |

**两组的 C-minus 都主动弃权**，理由是"缺少这一轮的新增效果信息，现有
中性证据不足以支持一次编辑"——这是干净的阴性结果，不是故障：Slow 在
只有中性事实（特征、候选、实际交付、动作计数，明确不含收益/损失/风险
结果/胜者标签）时，没有编出一条像样的修订，如实弃权。

**R（普通反思）** 两组写的都是"选择指导"类修改，核心是：证据不足以支持
候选特定效果时，倾向保留 identity，不因动作计数大、信号强但未验证局部化
而选程序。两组措辞高度一致。

**C（比较式修订）** 在两组走了不同路：g1 也是 PATCH 同一个
selection_guidance 面（但文字更强调"局部偏差假设 vs 缺失/周期证据的联合
比较"），g2 则是**新增一张有 observable_applicability 的技能卡**（条件：
`missing_fraction=='high' AND local_robust_z_peak=='high'`），只在高缺失+
高局部偏差同时出现时才建议"先核实缺失区与偏差区是否可分离，不可分离时
保持 identity"。**g2/C 因此只暴露到 8/40 条复核决策**——其余 32 条完全在
父知识下运行，与 F 逐位相同；g1/C 和两组的 R 都是全局性 PATCH，暴露率
都是 40/40。

## 4. 三种修订方式：哪些差异有证据支持，哪些仍不确定

- **C-minus（去掉新增效果信息）在两组都弃权**——这是本包证据最扎实的
  一条：**"重组中性事实本身"不足以让 Slow 产出一条修订**，增量确实
  依赖新增的效果反馈信息，而不是信息重新整理这件事本身。任务书路线
  判断第三条（"C 与 C-minus 都改善,需承认可能主要来自知识重组织"）
  在本包**不成立**，因为 C-minus 从未形成，无法比较。
- **R 与 C 均在 g1 上跑赢或跑输 F 方向不一致**，g2 上两者都跑赢 F 但
  互有胜负（C 略胜 g1，R 略胜 g2）——**没有证据支持"比较式组织比普通
  反思更好"这一假设**；样本小（各组各40条配对），本包不能给出稳定的
  优劣判断。按任务书路线判断第二条的精神（"R 与 C 均有帮助而没有证据
  支持 C 的额外价值,后续默认优先简单 R"），**后续默认应优先 R 而非
  默认追加 C 式比较框架**，但鉴于 R 在 g1 上明显更差，这个"优先"也
  只是工程简单性的默认，不是效果上的推荐。
- **C 与 F 的差距方向一致但没有一次跑赢 D-new-fixed**——按路线判断第
  四条，这更像"学到了一个更好的通用默认"（少数情况下更保守/更谨慎地
  比较），而不是真正的**条件化增量**：C 在 g2 唯一真正条件化的那次
  尝试（新增技能卡，仅 8/40 暴露）没有表现出比 g1 那种全局性 PATCH
  更好的效果，样本太小（8条）不足以下结论，但至少没有看到"条件化比
  全局修改更好"的迹象。

## 5. 剩余阻断在哪一环

参照任务书第七节的诊断框架：

- **观察**：公开特征/动作事实本身没有阻断——Slow 能读到、能引用（C 的
  两版修订都明确引用了局部偏差/缺失/周期证据的组合）。
- **提议**：R/C 都能提出编译通过、有暴露的修订，C-minus 在信息受限下
  正确弃权（不是提议环节失灵，是信息真的不够）。
- **执行**：确认交付行为确实随指导改变（R 的交付数下降），执行环节
  忠实反映了 Slow 写的东西。
- **更新算法本身**：这里是主要瓶颈——两版修订（无论普通反思还是比较式）
  产出的效果，量级都不足以超过一个完全不看数据的固定基线。这与
  DEV-DEPLOY-1 的结论指向同一处：**问题不在"Slow 能不能读懂反馈、能不能
  写出编译通过的指导"，而在于"写出来的指导能带来多少真实增量"——目前
  这个增量小到不足以抵消 Fast 逐序列决策本身的噪声/次优选择。**
- **后续适用性**：本包止步于同一批次形成→复核，没有测试"更新后的知识
  在更晚、完全独立的窗口上是否持续有效"，这一环仍未验证。

## 6. 路线判断（按任务书要求，一次性给出，不再发同类补丁包）

依据第4节的证据：**R 与 C 均有帮助但方向不完全一致，没有证据支持 C
的额外复杂度**——按任务书路线判断第二条，后续默认优先简单的 R 式反思，
不宣称两者已被证明等效。C-minus 的弃权确认了"增量依赖新增效果信息"，
排除了"仅靠重组织已有中性事实就能获得增量"这一解释。**C/F 差距没有
一次超过 D-new-fixed**，说明当前 Slow 更新更像是在学一个更好的通用
默认，而不是真正的按上下文条件化的增量——**条件化增量尚未成立**。
