## 1. 要回答的问题

离线经验能否让零反馈 Agent 更可靠地为零样本 TSFM 准备推理上下文，并减少逐任务试错？

已知情况：
- 按 Source 冻结的逐域选择，Test 上相对 192 点 +36.07 pp；
- 统一用 672 点、逐窗口标准化为 +34.43 pp；
- 这 36 pp 是“准备更长上下文”本身的收益，Agent 能贡献多少还不知道。

如果无卡 Agent 本来就会选足够长的历史，卡能带来的增量就很小；如果它习惯截短历史或用错标准化方式，就存在一个可以纠正的决策偏差。

## 2. 设计

- **Consumer**：Time-MoE-50M 零样本，不训练、不改权重。
- **动作**：每个案例选一种“上下文长度 × 标准化方式”组合，这个选择对 16 个实体、4 个预测起点都生效。
  - 长度：192 / 336 / 672 / 1344 / 2688 点；
  - 标准化：逐窗口（instance）或 T scaler（tscale）；
  - 共 10 个组合，历史不够长的组合标为不可用。
- **评分**：直接查缓存的零样本上下文筛查读数（服务器数值，本机只读 `_scratch/dev_aug_tsfm_native_server_pull/context_screen{,_select,_test}.json`），不重新推理。
- **Fast（零反馈）**：
  - 能看到的信息：案例卡（Consumer 说明、预测设置、各组合是否可用、T 段观察摘要），以及可选的 `history_profile` 工具（首个预测起点之前、按周汇总的历史统计，读不到起点之后的数据）。
  - 请求上限：最多 3 次，其中最后一次必须提交所选组合；允许 1 次格式纠正。
  - 不提供任何下游分数。
  - 没有合法提交的轨迹记为 INCOMPLETE，按默认的 192 点、逐窗口标准化交付，并单独计数。
- **一致性**：所有 Agent 臂的历史访问范围、候选动作和模型说明完全相同，无卡臂不会被限制在 192 点。
- **Source**：24 例，跑无卡 Agent，查明它实际会怎么选。
- **Slow**：读取 Source 的选择过程、所选组合的真实结果和全部 10 个组合的结果，写出共享卡 2 张、每域卡各 2 张，共 8 次调用；可以选择不出卡（KEEP）。
- **Select**：24 例。J = 所选组合的误差 ÷ 192 点基线的误差，取均值；域卡按域取 J 最小，共享卡取三域平均 J 最小。平局时依次比较更少 token、更小的槽位编号。
- **Test**：40 例，三臂为无卡、共享卡、域卡。参照为：
  - 192 点、逐窗口标准化（基线）；
  - 统一 672 点、逐窗口标准化（Source 上表现最好的统一方案）；
  - Source 冻结的逐域固定选择。
- **读数**：各臂相对基线的收益；成对差值（域卡 − 无卡、共享卡 − 无卡、域卡 − 共享卡、各臂 − 参照）及其胜负和聚类 bootstrap 区间；各臂选择分布、请求次数、token 数、INCOMPLETE 数。

## 3. 预算与并行

- 上限：12M token、1000 个逻辑请求，墙钟 12 h。
- LLM 并行 6 路；本机 DLinear 包同时在用同一个中转，所以并行数取得偏小。
- 传输：流式，每个请求最多重试一次，重试前等 90 s；阶段内仍有被传输打断的轨迹时停止该阶段，续跑时从断点继续。

## 4. 停止条件

读数和报告写完即停止，不自动修订卡片，也不扩大长度菜单。
